# feat(remote-mcp): route remote connection traffic through declared SOCKS5 proxy

## Thinking Path

> 1. **Understand the Problem and System Context:**
>    - Paperclip supports remote MCP servers via `mcp_remote` connections.
>    - Currently, outbound HTTP/HTTPS requests (health checks, catalog discovery, OAuth discovery/DCR/token exchange, and runtime gateway `tools/call`) are issued directly from the Paperclip host using standard pinned agent dispatchers.
>    - In secure network environments (e.g. enterprise deployments, isolated VPCs, border networks), remote MCP services are only accessible through a SOCKS5 proxy or bastion jump host. Target hostnames often exist only in private DNS zones reachable through the proxy.
>    - Direct connection attempts fail with DNS resolution errors (`ENOTFOUND`) or network timeouts, blocking agent usage of remote MCP tools.
> 2. **Design the Minimal, Direct Fix:**
>    - **Configuration Surface:**
>      - `mcp_remote` connections declare `config.proxy`, formatted as `socks5h://[user:pass@]host[:port]`. Protocol must strictly be `socks5h:`. Default port is 1080.
>      - Any other protocol (e.g. `http:`, `socks5:`, `socks4:`) is rejected at connection save and use time with code `mcp_remote_proxy_invalid`.
>    - **Egress Guard Rules:**
>      - The declared proxy endpoint may be loopback (`127.0.0.1`) or private network IP/host.
>      - Target-URL egress checks still apply (valid HTTP/HTTPS scheme, denial of link-local and private IP literals).
>      - Hostname resolution is not done locally; it is delegated to the SOCKS5 proxy via SOCKS5 domain address type (`ATYP = 0x03`).
>    - **Transport & Tunneling:**
>      - When `proxy` is declared, requests establish a SOCKS5 tunnel using RFC 1928 handshake (methods `0x00` NO_AUTH and `0x02` USER_PASS; command `0x01` CONNECT).
>      - For HTTPS targets, end-to-end TLS is negotiated over the established tunnel, verifying server certificate and setting SNI to the target hostname.
>      - Direct-connection fallback is strictly prohibited: if proxy connection or handshake fails, the request fails immediately.
>      - Redirects remain manual and are subject to the same egress guard rules.
>    - **Unproxied Invariance:**
>      - Connections without a proxy retain the current pinned transport behavior completely unchanged.
> 3. **Verify:**
>    - Regression tests in `server/src/__tests__/remote-mcp-socks-proxy.test.ts` verify:
>      1) Catalog refresh tunnels through declared SOCKS5 proxy with target domain in SOCKS5 handshake (`ATYP = 0x03`).
>      2) Gateway `tools/call` tunnels through declared SOCKS5 proxy to remote endpoint.
>      3) Unproxied connections retain pinned transport unchanged.
>      4) Unsupported or malformed proxy values are rejected when saved and when used (`mcp_remote_proxy_invalid`).
>      5) Unreachable proxy fails without direct fallback, and target-URL egress guards still apply to proxied connections.

### Issue Summary: Remote MCP connections cannot route through a SOCKS5 proxy

**What happened?**
Remote MCP connections (`mcp_remote`) currently execute all outbound requests (catalog reads, health probes, OAuth flows, gateway `tools/call`) directly from the host. When remote MCP servers are accessible only via private network tunnels or boundary jump hosts requiring SOCKS5 proxy routing, requests fail because target hostnames cannot be resolved locally and direct egress is blocked.

**What did you expect to happen?**
1. An `mcp_remote` connection can declare `config.proxy`, for example `socks5h://127.0.0.1:1082`.
2. Every outbound request for that connection tunnels through the proxy, with target hostname resolution delegated to the proxy (`ATYP = 0x03`).
3. TLS stays end-to-end, with certificate verified against target hostname and SNI set to it.
4. Egress guards permit loopback/private proxy endpoints, enforce target-URL checks, and retain manual redirect handling.
5. Unsupported/malformed proxy values are rejected when saved and when used with code `mcp_remote_proxy_invalid`. Proxy failures error immediately without direct fallback.
6. Connections without a proxy retain the pinned transport unchanged.

**Steps to reproduce**
1. Configure an `mcp_remote` connection with an unroutable internal hostname (e.g. `http://unroutable-mcp-target.internal:8080/mcp`) accessible only via a local SOCKS5 proxy (`socks5h://127.0.0.1:1082`).
2. Trigger connection catalog refresh or gateway tool execution.
3. Observe that without proxy support, the request fails with `ENOTFOUND unroutable-mcp-target.internal`.

**Paperclip version or commit**
`master` at `01d9a121859a3d8298dce91452f75516e837e819` and release tag `v2026.916.1`.

## What Changed

- `server/src/services/remote-http-endpoint-guard.ts`:
  - Added `parseRemoteHttpProxy` and `assertProxiedRemoteHttpEndpoint`.
  - Strictly validates `socks5h:` protocol, allows loopback and private proxy endpoints, and validates target URLs without local DNS resolution.
- `server/src/services/remote-http-fetch.ts`:
  - Added `proxy` to `GuardedRemoteHttpFetchOptions`.
  - Implemented `proxiedRequest`, `openProxiedSocket`, `performSocks5Handshake` (delegating hostname resolution via `ATYP = 0x03`), persistent `Socks5SocketReader`, and TLS wrapping with target `servername`.
  - Prohibited fallback on proxy failure and preserved manual redirect policies.
- `server/src/services/tool-access.ts`:
  - Validated `config.proxy` at connection save time.
  - Passed `config.proxy` across `assertRemoteEndpointAllowed`, `remoteHttpFetchOptions`, `fetchRemoteHttpUrl`, `remoteTools`, `endpointsFromMetadataUrl`, `registerOAuthClient`, and `exchangeOAuthToken`.
- `server/src/services/tool-gateway.ts`:
  - Extracted `config.proxy` from connection configuration and passed it into `remoteHttpFetchOptions` for remote context method calls and `dispatchRemote` tool execution.
- `server/src/__tests__/remote-mcp-socks-proxy.test.ts`:
  - Added comprehensive regression test suite verifying proxy tunneling for catalog and gateway tools/call, SOCKS5 domain resolution, unproxied transport invariance, invalid/unsupported proxy rejection, and fail-closed behavior without fallback.
