# fix(tool-gateway): scope named gateway discovery to profile tools and bound queries

## Thinking Path

> 1. **Understand the Problem and System Context:**
>    - Named MCP gateways expose tools to connected agents and clients via `tools/list`.
>    - Previously, `listToolsForContext` loaded `connectedMcpToolsForCompany` for the whole company catalog, evaluating all company MCP tools against policy even if the gateway was explicitly assigned a narrow profile (e.g. 2 tools out of 1,350).
>    - On large instances with many connections (e.g. 31 connections, 1,350+ tools), evaluating all candidates triggered an N+1 query storm: re-reading `tool_policies`, `tool_profile_bindings`, `tool_profiles`, `tool_profile_entries`, and `tool_mcp_gateways` for every candidate tool (over 12,000 queries per `tools/list` call), causing discovery to take 30+ seconds and timing out client startup (such as Codex MCP bridge).
>    - Furthermore, if a runtime gateway had `tool_mcp_gateways.profile_id` set but no `tool_profile_bindings` row, `effectiveProfiles` fell back to the agent's profiles, leaking all agent tools to the gateway.
> 2. **Design the Minimal, Direct Fix:**
>    - **Profile Scoping:**
>      - When a gateway has an assigned profile whose `defaultAction !== "allow"`, `listToolsForContext` queries candidate tools scoped to that profile via `connectedMcpToolsForProfile(companyId, profileId, cache)` rather than the entire company catalog.
>      - Built-in tools and connected tools are filtered by the profile's include entries.
>    - **Gateway Profile Authority:**
>      - In `effectiveProfiles` (`tool-access-policy.ts`), when `ctx.gatewayId` is present and `gateway?.profileId` exists, the gateway profile is treated as authoritative (priority 0). If missing from `matchingBindings`, a synthesized binding is added.
>      - Agent-scope profiles are never allowed to widen a gateway-scoped evaluation: when `ctx.gatewayId` is present, additive app profiles are disabled (`includeAdditiveAppProfiles = false`).
>    - **Query Bounding & Context Caching:**
>      - Introduced `ToolEvaluationContextCache` and `createToolEvaluationContextCache(db, companyId)` to cache single-flight promises for policies, bindings, gateway records, profiles, and profile entries across a single discovery call.
>      - Candidate tool discovery (`connectedMcpToolsForProfile` / `connectedMcpToolsForCompany`) primes catalog entries, connections, and applications directly into the cache.
>      - Policy evaluation reuses this cache for all candidates, bounding policy-context DB queries to <= 15 queries regardless of catalog tool volume.
> 3. **Verify:**
>    - Regression tests in `server/src/__tests__/scope-named-gateway-tool-discovery.test.ts` prove:
>      1) A profiled named gateway evaluates only its profile's candidates.
>      2) A runtime gateway with `profile_id` and no binding row lists only its profile's tools, never the agent's.
>      3) One `tools/list` issues a bounded number of policy-context queries (<= 15) independent of company tool count.
>      4) Decisions for mixed allow, deny, and require-approval toolsets are unchanged.

### Issue Summary: Named MCP gateway discovery evaluates all company tools with uncached queries, causing 30s timeouts

**What happened?**
When an agent or client connected to a named MCP gateway and issued `tools/list`, Paperclip loaded all tools across the entire company catalog. For each candidate tool, `policyService.decide` re-executed queries for `tool_policies`, `tool_profile_bindings`, `tool_profiles`, and `tool_profile_entries`. In environments with many connections (e.g. 30+ connections and 1,000+ tools), a single `tools/list` executed over 12,000 database queries and took 30+ seconds, causing MCP clients like Codex to drop the connection due to startup timeouts. In addition, when a gateway had an assigned profile but no explicit gateway binding row in `tool_profile_bindings`, it fell back to evaluating the agent's profile bindings, erroneously exposing tools outside the gateway's intended profile.

**What did you expect to happen?**
1. A named gateway assigned a profile evaluates only tools permitted by that profile.
2. The gateway's `profile_id` is authoritative, even without an explicit gateway binding row; agent-scope profiles never widen it.
3. Database queries for policy context are loaded once and reused across all candidate evaluations, bounding query count to <= 15 per call.
4. Tool decisions (allow, deny, require approval) and token-action gating remain unchanged for correctly resolving gateways.

**Steps to reproduce**
1. Create a company with 10+ MCP connections and 100+ catalog tools.
2. Create a named MCP gateway assigned a restricted profile with 1 included tool.
3. Request `tools/list` through the gateway bearer.
4. Observe that all 100+ tools are evaluated, issuing hundreds of redundant SQL queries, and taking multiple seconds to respond.

## What Changed

- `server/src/services/tool-access-policy.ts`:
  - Defined `ToolEvaluationContextCache` interface and exported `createToolEvaluationContextCache(db, companyId)`.
  - Added `createContextCache` to `toolAccessPolicyService`.
  - Updated `loadContext`, `effectiveProfiles`, `explicitGrant`, and `decide` to accept an optional `ToolEvaluationContextCache`.
  - In `effectiveProfiles`: when `ctx.gatewayId` is present and `gateway?.profileId` exists, synthesized a gateway binding at priority 0 when missing from `matchingBindings`, and disabled additive agent/app profiles (`includeAdditiveAppProfiles: false`).
- `server/src/services/tool-gateway.ts`:
  - Added `defaultProfileMode` to `ToolGatewaySession` and populated it in `namedGatewaySessionFromBearer`.
  - Extracted `mapRowsToToolGatewayDescriptors(rows)` to share client-safe naming and metadata mapping.
  - Implemented `connectedMcpToolsForProfile(companyId, profileId, cache)` to query and filter candidate tools matching profile selectors (connection, application, catalog entry, tool name, risk level).
  - Updated `connectedMcpToolsForCompany(companyId, cache)` to prime catalog entries, connections, and applications into the cache.
  - Updated `listToolsForContext(session)`: evaluates only profile candidate tools when profile `defaultAction !== "allow"`, filters built-in tools against profile include entries, and passes the request-scoped cache to `policyService.decide`.
- `server/src/__tests__/scope-named-gateway-tool-discovery.test.ts`:
  - Added unit and integration regression tests covering candidate tool scoping, gateway profile authoritativeness without binding rows, query count bounding under tool volume, and allow/deny/approval decision preservation.
