# 25 — A remote MCP connection can route its traffic through a declared SOCKS5 proxy

**ready.** An `mcp_remote` connection can declare `config.proxy` (e.g. `socks5h://127.0.0.1:1082`). Outbound requests (catalog reads/health probes, OAuth discovery, DCR, token calls, and gateway `tools/call`) tunnel through the proxy with hostname resolution delegated to the proxy (`ATYP = 0x03`). End-to-end TLS is preserved with target SNI and certificate verification. Egress guards permit loopback/private proxies while enforcing target URL checks. Malformed/unsupported proxy formats are rejected with `mcp_remote_proxy_invalid`, and no direct fallback occurs on proxy failure. Unproxied connections remain unchanged.

## Review outcome

Problem: Remote MCP connections (`mcp_remote`) currently execute outbound HTTP/HTTPS requests directly from the Paperclip host using standard pinned agent dispatchers. In enterprise environments where remote MCP servers are accessible only via private network tunnels or boundary jump hosts, connections cannot route through a declared SOCKS5 proxy, and target hostnames cannot be resolved remotely by the proxy.

Implementation: Allows `mcp_remote` connections to declare `config.proxy` formatted as `socks5h://[user:pass@]host[:port]`. Tunnels all outbound traffic (catalog discovery, OAuth discovery/DCR/token exchange, and runtime gateway `tools/call`) through the SOCKS5 proxy, passing the target hostname for remote DNS resolution. Preserves end-to-end TLS and server certificate verification with SNI. Validates proxy format with error code `mcp_remote_proxy_invalid` and refuses direct connection fallbacks.
