## Initial source findings requiring regression proof

These are source-level findings and concrete reproduction designs. None was
executed by this reviewer. Priority expresses potential impact, not proven
production exploitation.

### 14-1: Provider selector removed (P1)

At `server/src/services/tool-access-policy.ts:357`, the change removes
`match("providerType", "providerTypes", ctx.providerType)` while adding legacy
tool names. The `providerType` and `providerTypes` fields are still supplied by
policy/scope consumers. Removing their predicate means a selector can match
requests from a different provider.

Restore that predicate. Regression proof should exercise actual policy decisions
for the same tool name with different providers, using singular and plural
selectors and a scoped/boundary consumer.

### 14-2: New catalog entries can redirect existing names (P1)

`server/src/services/tool-gateway.ts:1359–1423` sorts connection creation time
before catalog-entry creation time and reconstructs assignments in memory.
Suppose newer connection B already exposes `app_search`; discovering `search`
on older connection A puts A first and gives it the unsuffixed name. B is
renamed, so existing clients can address a different connection under the old
name. Removal or temporary ineligibility of the prior owner can likewise
change the reconstructed assignment.

The existing test at `server/src/__tests__/tool-gateway.test.ts:5709` adds a
newer connection and checks that a name exists. It does not assert which remote
connection executes each call. Add older-connection discovery, temporary
ineligibility, and exact dispatch identity tests. A stable assignment mechanism
must preserve tool identity when the eligible catalog changes.

### 14-3: Reserved gateway names are not reserved (P1/P2)

`claimedNames` starts empty at `server/src/services/tool-gateway.ts:1381` and
tracks connected catalog tools only. An application key `paperclip` with tool
`list_resources` produces `paperclip_list_resources`. The named-gateway route
at `server/src/routes/tool-gateway.ts:147–165` intercepts that string as a
context method, so it never calls the advertised connected tool. Application
`search` with tool `tools` collides with virtual `search_tools`.

Account for the complete exposed namespace, including context, virtual,
plugin, GitHub, and Slack tools. Prove the exact remote target through a route
call, not only uniqueness in a helper result.

### 14-4: The every-listed-tool format outcome is not covered (P2)

Built-in fixture/self descriptors at
`server/src/services/tool-gateway.ts:976–1073` still contain `:`. The format
regression at `tool-gateway.test.ts:5546` selects only connected applications
through a deny-by-default profile. It cannot prove the blanket requirement that
every listed tool is client-safe.

Add a profile that exposes built-ins and cover the session listing route, or
obtain explicit agreement to narrow the outcome to connected catalog tools.

### 14-5: Permanent old-name resolution remains (contract concern)

`server/src/services/tool-gateway.ts:2835–2842` accepts both current and old
gateway names. `server/src/services/tool-access-policy.ts:359–364,681`
continues matching old policy and scope names. Change 16 migrates only profile
entries, not policies, trust rules, approvals, or idempotency identity. The
recorded one-path transition requirement therefore remains unsatisfied in
source. Resolve the stored-data transition and maintainer compatibility
direction explicitly. Source comments naming “Change 14” or “report fixtures”
should describe the actual contract instead of fork review history.

### 16-1: Migration can broaden a connection-specific grant (P1)

`server/src/services/tool-profile-migration.ts:73–81,105–130` reduces an old
connection-qualified name to a global catalog name while keeping selector type
`tool_name`. A rule allowing `mcp.app-<connection-A>:search` can then match
every evaluated catalog tool named `search`, including connection B.

Resolve old identities unambiguously and preserve the allowed/denied set.
Existing connection-specific entries may need a `catalog_entry` selector rather
than an unqualified name. Seed two same-named tools on different connections;
assert exact before/after permissions, including exclusion rules.

### 16-2: Substring guesses can rewrite unrelated plugin selectors (P1)

At `server/src/services/tool-profile-migration.ts:108–115`, suffix and
substring matches do not require application/connection identity. For example,
`plugin_web_search` matches an MCP catalog entry named `search` and can be
rewritten to that catalog name. The fixture/plugin exclusions at lines 57–62
do not protect this form. Multiple possible catalog matches choose the first
unordered row.

Test unrelated plugin names, normalized-name collisions such as `foo.bar` and
`foo-bar`, long/truncated names, and multiple applications. Unknown or ambiguous
identity must not be guessed. The current migration also handles arbitrary
colon-bearing strings, increasing the need for exact identity resolution.

### 16-3: Startup rewrite can overwrite concurrent edits (P2)

The migration reads entries and later updates each by `id` alone at line 130.
Another server or operator can change that entry between the read and write.
Preserve concurrency semantics and test a changed selector/name before update.
Every startup rescans and reruns the heuristic rewrite; no version/completed
state is recorded. The root must settle the intended migration authority and
retain real startup/restart proof against a database.

### 05-1: Depth cutoff returns unredacted data (P1; initial audit)

At `server/src/middleware/http-log-redaction.ts:409`, depth >=6 returns the
original subtree. Known credential fields nested below that boundary are then
outside the recursive redactor and outside the explicit Pino redact paths.
Add complete-stream sentinel tests at and beyond the boundary. Preserve useful
shallow fields without allowing an uninspected subtree through.

### 05-2: Nested child bindings bypass the log-call hook (P1; initial audit)

`server/src/middleware/logger.ts` sanitizes log-call arguments in
`hooks.logMethod`. Child bindings are serialized at `child()` construction.
Explicit Pino paths cover known top-level fields and request/response headers,
not `root.child({ context: { gatewayToken: sentinel } })` or arbitrary
mixed-case nested binding fields. The current test at
`server/src/__tests__/http-log-redaction.test.ts:1016` covers top-level known
fields and the dedicated `headers` serializer only.

Add nested and mixed-case child-binding tests against the complete serialized
stream. The `fix_redaction` worker owns final reproduction, repair, and status.
