## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - Code tasks move through review and approval stages, and the final approval closes the issue as `done`
> - Today an issue can reach `done` while its pull request is still open, not merged, or failing checks. Nothing checks the delivery (#11145)
> - #11196 adds an opt-in `evidenceRequired` policy flag and records evidence with the decision, but the server cannot check that evidence
> - This pull request builds on #11196. With `evidenceRequired`, the server verifies the delivery against GitHub before it writes the terminal decision. It checks that the exact reviewed head is merged, that the base branch contains it, and that the checks passed. The repository, pull request, and credentials come only from server-held state
> - The benefit is that an evidence-gated issue cannot close on a claim alone, and a caller cannot point the verification at a repository or host that it chooses

## What Changed

- `packages/db`: `issue_execution_decisions.evidence jsonb` (migration `0284_keen_mac_gargan`, generated with `pnpm --filter @paperclipai/db generate`).
- `packages/shared`:
  - `evidenceRequired` on the execution policy.
  - The request evidence schema is strict: `pr`, `mergedSha` (40 hex characters), `checkRun`, and `note`.
  - The server-written evidence record and receipt types. Callers cannot send `verified` or `receipt`.
- `server/src/services/delivery-verification.ts` (new): resolves the target only from server-held state:
  - the repository remote and the base branch, from the issue's execution workspace or else the project's primary workspace
  - the pull request, from the issue's `pull_request` work product
  - the reviewed head, from its `commit` work product

  It then verifies against `api.github.com` with company-scoped credentials: the managed GitHub identity, or else a company secret. It never uses process environment tokens. It checks:
  - the PR is merged, and its head is exactly the reviewed head
  - the merged SHA matches
  - the live base contains the head (`ahead_by === 0`)
  - every check run passed, with all pages read up to `total_count`

  Zero checks, a short read, a non-github.com remote, or an unconfigured base fail closed with stable `delivery_*` codes.
- `server/src/services/issue-execution-policy.ts`:
  - The gate reads the persisted and the incoming policy, so the closing request cannot lower it.
  - `evidenceSource` (`request` or `system`) is required at each call site. A system-initiated terminal approval under `evidenceRequired` is refused with an actionable message.
  - An evidence-gated issue can reach `done` only through a verified terminal stage decision. Replacing stages, removing the policy, or a board override cannot close it.
- `server/src/routes/issues.ts`: the PATCH and comment routes verify before the terminal write. They re-check the target binding under the row lock (`delivery_verification_stale`) and persist the server-written receipt. `recovery-actions/resolve`, `execution-workspaces` reconcile, and the provider-quota monitor declare `system`.
- `server/src/services/issue-thread-interactions.ts`: an approving native completion review card cannot close an evidence-gated issue without verified evidence.
- `doc/execution-semantics.md` §14 documents the covered paths and the scope limit.

## Risks

- This is a core feature. It is opt-in per policy (`evidenceRequired`), and policies without it do not change.
- **Scope limit:** the native runtime's own status-decision committer does not use this gate. A refusal inside that retried finalization would loop forever. An issue whose completion must be verified should not also be completable by the native runtime's status authority. `doc/execution-semantics.md` §14 says so.
- Under `evidenceRequired`, an approving comment without evidence is refused before the comment is stored. Recovery-action resolution cannot close such an issue.
- Only github.com is supported. GitHub Enterprise, Gitea, and other hosts fail closed with `delivery_unverified_unsupported_provider`.
- Provider state can change between the check and the write. The receipt records `verifiedAt`.
- `issue_execution_decisions.evidence` has no API read path yet.
