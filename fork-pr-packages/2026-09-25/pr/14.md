# fix(tool-gateway): assign client-safe tool names and preserve legacy tool transition

## Thinking Path

> - Paperclip provides an MCP tool gateway (`/mcp/gateways/:gatewayId` and `/api/tool-gateway/tools`) exposing tools from connected MCP servers and internal adapters to agents and external clients.
> - Strict MCP client runtimes (such as Google Antigravity CLI `agy`, and various LLM function-calling wrappers) enforce naming constraints on tools, e.g. `^[a-zA-Z0-9_-]{1,64}$`, and name their proxied tools as `mcp_<server>_<tool>`.
> - Paperclip historically named connected MCP tools using dots and colons in the form `mcp.<appKey>-<connId8>:<tool>` (e.g., `mcp.harness-mcp-openobserve-12345678:echo`) or `${conn.name}:${tool.name}`.
> - Because `:` and `.` violate client validation regexes, and combined server prefix + tool name frequently exceeds length caps, strict MCP clients rejected all proxied tools on the gateway.
> - Furthermore, colliding tools were previously disambiguated dynamically by appending index suffixes to all occurrences, causing existing tools to be renamed when a new connection or tool was added.
> - This pull request assigns client-safe tool names matching `^[A-Za-z0-9_-]{1,40}$` formatted as `<application key>_<tool>`, deterministically preserves stability on additive connections, and guarantees full backward compatibility for dispatch, approvals, trust rules, and profile entries created under legacy names.

## Linked Issues or Issue Description

No existing public GitHub issue was found addressing MCP client-safe tool name restrictions or 64-character tool-name limits. Issue #11372 addressed tool profile matching with normalized names, and PR #12872 addressed tool display names/descriptions, but neither resolved gateway tool name validation for strict MCP clients.

### Drafted Bug Report: Gateway tool names contain invalid characters (`:`, `.`) and exceed length limits for strict MCP clients

**What happened?**
When connecting strict Model Context Protocol (MCP) clients (such as Google Antigravity CLI `agy` or function-calling tool registries that enforce `^[a-zA-Z0-9_-]{1,64}$` for `mcp_<server>_<tool>`) to a Paperclip MCP gateway (`/mcp/gateways/:gatewayId` or `/api/tool-gateway/tools`), all assigned tools are rejected during tool discovery.
The gateway formatted tool names as `mcp.<appKey>-<connId8>:<tool>` or `${connection.name}:${tool.name}`, containing colons (`:`) and periods (`.`). Additionally, when names collided across connections, Paperclip dynamically renamed all occurrences, breaking tool name stability.

**What did you expect to happen?**
1. Every tool listed by Paperclip's MCP tool gateway has a client-safe name matching `^[A-Za-z0-9_-]{1,40}$`, formatted as `<application key>_<tool>` (e.g. `openobserve_searchsql`, `gitea_pull-request-write`).
2. Adding a new connection, catalog entry, or tool never renames an existing assigned tool.
3. Pre-upgrade approvals, trust rules, and profile entries created under legacy `mcp.<app>-<connId8>:<tool>` names continue to match and execute smoothly.

**Steps to reproduce**
1. Connect an MCP server (e.g., `harness-mcp-openobserve`) to Paperclip.
2. Query `/mcp/gateways/:gatewayId` or `/api/tool-gateway/tools`.
3. Observe tool names like `mcp-remote-fixture:echo` or `mcp.harness-mcp-openobserve-12345678:echo`.
4. Connect an MCP client that enforces standard alphanumeric/underscore/dash identifiers. All tools fail client-side schema validation and are dropped.

**Paperclip version or commit**
`master` at `efce9356b553a08f77a5877bb0ceac68d2cc4ad8` and release tag `v2026.916.1`.

**Deployment mode**
Self-hosted server and cloud instances.

## What Changed

- `server/src/services/tool-gateway.ts`:
  - Implemented `clientSafeSlug` to normalize strings with lowercase alphanumerics, underscores, and dashes (`replace(/[^a-z0-9_-]+/g, "-")`).
  - Added `formatClientSafeGatewayToolBaseName` to produce deterministic names of the form `${appSlug}_${toolSlug}` strictly bounded to 40 characters.
  - Implemented deterministic disambiguation in `connectedMcpToolsForCompany`: sorted connections and catalog entries by creation time and ID (`(connection.createdAt ASC, connection.id ASC, catalogEntry.createdAt ASC, catalogEntry.id ASC)`). The primary connection retains the clean base name; subsequent colliding connections receive deterministic numeric/hash suffixes. Adding a new connection never mutates existing assigned tool names.
  - Retained `legacyToolName` on internal gateway descriptors and updated `findToolForSession` to resolve tools by either their new client-safe name or their pre-upgrade legacy name.
  - Updated `approvalSnapshotsMatch` to treat legacy-to-client-safe gateway tool name transitions as equivalent when underlying connection, upstream tool, catalog ID, and parameter schemas match.
- `packages/shared/src/types/tool-access.ts`:
  - Added optional `legacyToolName` and `legacyToolNames` fields to `ToolAccessDecisionInput['request']` and `ToolAccessContext`.
- `server/src/services/tool-access-policy.ts`:
  - Updated `selectorMatches`, `profileEntryMatches`, and `scopeAllowsTool` to match candidate tools against both their client-safe name and legacy tool names, ensuring existing tool-access profiles and trust rules remain fully effective.
- `server/src/__tests__/tool-gateway.test.ts`:
  - Added regression test `lists client-safe tool names matching ^[A-Za-z0-9_-]{1,40}$ for harness-mcp-openobserve`.
  - Added behavioral test for executing tools by their new client-safe names.
  - Added behavioral test verifying tool name stability when a second connection for the same application is added.
  - Added behavioral tests verifying that approvals, trust rules, and tool profile entries created under legacy names remain valid and enforceable after upgrade.

## Risks

- **Low-to-moderate:** Tool names advertised on `/mcp/gateways/:gatewayId` and `/api/tool-gateway/tools` change from `mcp.<app>-<connId8>:<tool>` to `<application key>_<tool>`.
- Client agents receiving refreshed tool lists will see the new client-safe names. Tool dispatch, session lookups, policy checks, trust rules, and approvals accept both the new name and the legacy name, ensuring zero disruption to in-flight or historical executions.
