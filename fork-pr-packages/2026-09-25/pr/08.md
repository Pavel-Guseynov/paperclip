## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - Before an agent runs in an execution workspace, Paperclip validates the git worktree. When the validation fails, it records a typed diagnosis, for example `git_worktree_branch_incoherence` with the live HEAD and a safe repair
> - Recovery then creates an operator-facing recovery action from that diagnosis
> - But a later generic failure on the same issue, or a stranded-issue sweep, replaces the recovery action's cause and evidence with generic text. A wrapped validation failure (in `Error.cause`) is not recognized, and a failed review participant's validation failure is not surfaced as one
> - So the operator loses the precise diagnosis and the recovery action that tells them how to reissue from the exact commit (#7398, #8767, #10497)
> - This pull request keeps the typed workspace-validation diagnosis ahead of generic failures, recognizes wrapped validation failures, and surfaces a review participant's validation failure with its own notice
> - The benefit is that operators keep the actionable diagnosis until they resolve it, and no unique commit in a detached workspace is lost to a generic retry

## What Changed

- `server/src/services/heartbeat.ts`: new exported `findWorkspaceValidationFailure` follows `Error.cause` chains, with cycle protection. The four call sites that detect a workspace validation failure use it. The caught error is rethrown unchanged.
- `server/src/services/recovery/service.ts`:
  - `resolveStrandedRecoveryCause` keeps `workspace_validation_failed` ahead of a generic explicit cause. A non-generic explicit cause still wins.
  - A failed review participant run with a workspace validation failure escalates with a typed notice. This applies only to unsuccessful terminal runs.
- `server/src/services/recovery/stranded-notice.ts`: new `buildExecutionReviewParticipantWorkspaceValidationNoticeSeed`. It names the diagnosis and the next action. When the participant is also not invokable, the notice says so too.
- `server/src/services/issue-recovery-actions.ts`:
  - A generic sweep that attempts no recovery does not replace an active `workspace_validation` action. A later failure that names its own cause still supersedes it.
  - On preserving writes, `workspaceValidation` evidence is deep-merged. Replacing writes keep upstream's semantics.
- Tests (real temporary git repositories and embedded Postgres):
  - `server/src/__tests__/workspace-validation-recovery-precedence.test.ts`:
    - a detached HEAD with a unique commit keeps the exact SHA and reissue base
    - a dirty worktree is not repaired
    - wrapped failures are recognized
    - a sweep-level test: typed run → sweep → newer generic run → sweep, with the action unchanged
    - the review participant notice, with the participant invokable and not invokable
    - a succeeded run with a payload is ignored
    - the evidence merge semantics
  - `legacy-execution-recovery.test.ts` pins upstream's reconciliation rule for workspace-validation runs.
  - `stranded-notice.test.ts` covers the new notice.
