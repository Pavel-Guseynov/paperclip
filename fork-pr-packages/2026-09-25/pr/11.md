## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - Native runner agents hand files back to Paperclip as durable deliverables
> - Before it registers a deliverable, the server verifies the opened file descriptor. On Darwin it reads the file path from `lsof -F0n`
> - `lsof` escapes each byte it will not print as `\xNN`, and it doubles a literal backslash. The server used that field verbatim
> - So `realpath` failed with ENOENT for any non-ASCII filename, such as `猫 picture.png` or `résumé report.pdf`, and the deliverable could not be registered
> - This pull request decodes the `lsof` name field exactly and pins the `lsof` locale so the field has one format on every host
> - The benefit is that deliverables with non-ASCII names register on macOS, and the descriptor check keeps its fail-closed behavior

## Linked Issues or Issue Description

No issue exists. This is the bug report, in the shape of `.github/ISSUE_TEMPLATE/bug_report.yml`.

**What happened?**
On macOS, `register_deliverable` failed for a file named `猫 picture.png`. The error was `ENOENT: no such file or directory, realpath '…/out/\xe7\x8c\xab picture.png'` from `readVerifiedWorkspaceFile` in `server/src/services/native-runtime/native-runner-file-handoff.ts`.

**What did you expect to happen?**
The deliverable registers, the same as a file with an ASCII name.

**Steps to reproduce**
1. On macOS, create a workspace file with a non-ASCII name (for example `猫 picture.png`).
2. Register it as a native runner deliverable.
3. Descriptor verification runs `/usr/sbin/lsof -a -p <pid> -d <fd> -F0n`. Under the C locale (or no locale) it prints `\xe7\x8c\xab picture.png`, `realpath` fails, and the delivery fails.

The existing test `server/src/__tests__/file-delivery-bridges.test.ts` ("registers native files with API tools disabled and returns durable download receipts") already fails on `master` on macOS for this reason.

**Paperclip version or commit**
`master` at 7b7c4d4172d6aac14919e2682b702ae87bc17653.

**Deployment mode**
Any deployment that runs the server on macOS. Linux reads `/proc/self/fd` and is not affected.

## What Changed

- `server/src/services/native-runtime/native-runner-file-handoff.ts`:
  - New `decodeLsofPath()` decodes contiguous `\xNN` byte runs as UTF-8 and `\\` as one backslash, in one left-to-right pass. It returns all other text verbatim.
  - A byte run that is not valid UTF-8 fails closed with `paperclip_runner_file_handoff_descriptor_unverifiable`. Before, it became U+FFFD and failed as a bare ENOENT.
  - `openedFilePath()` runs `lsof` with `LC_ALL=C`. Under a UTF-8 locale `lsof` prints multi-byte characters verbatim, so the field format depended on the server's locale.
- `server/src/services/native-runtime/native-runner-file-handoff.test.ts`: a Darwin-gated behavioral test registers `猫 picture.txt`, `résumé report.txt`, a name that contains a literal `\x41`, and `plain report.txt` through the real handoff path with the real `/usr/sbin/lsof`, under `LANG=en_US.UTF-8`. Direct decoder assertions cover only the invalid-UTF-8 byte run, because APFS refuses such filenames (`EILSEQ`).

## Risks

- Low risk. The change affects only the Darwin descriptor path.
- `lsof` now runs with a replacement environment of `LC_ALL=C` only. It is called by absolute path and needs no `PATH` or `HOME`. `env -i /usr/sbin/lsof …` gives the same output.
- A path that contains other `lsof` escapes still fails closed. The content-reference validation already rejects control characters.
