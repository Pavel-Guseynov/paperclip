# fix(issues): do not cancel calling run when recording stage decision

> ## Thinking Path
>
> 1. **Understand Goal & Context:**
>    - When an agent completes a review or approval stage, it submits a PATCH to `/api/issues/:id` recording its decision (e.g., `status: "done"` to approve, or `status: "in_progress"` to request changes).
>    - The execution-policy handler generates a transition that reassigns the issue to the next stage participant or the return assignee.
>    - Because `assigneeWillChange` is true, the route invokes `resolveActiveIssueRun(existing)` and cancels any active run on the issue with `errorCode: "issue_reassigned"` before the update transaction commits and before the 2xx response is returned.
>    - As a result, the agent run that itself sent the PATCH request gets cancelled mid-request, its process group is terminated (e.g., `curl` exits with 137), and it is recorded as `cancelled` with `issue_reassigned` and failed liveness, even though its decision successfully commits fractions of a second later.
>    - Any retry by the agent fails with 422 because the stage has already transitioned.
> 2. **Design the Minimal, Direct Fix:**
>    - When a PATCH mutation records an execution-policy stage decision (`transition.decision` is truthy), the run making the request (identified via `actor.runId` or header `x-paperclip-run-id`) must not be cancelled by the reassignment / terminalization stop logic.
>    - Update `resolveActiveIssueRun` to accept `options?: { excludeRunId?: string | null }`.
>    - When checking `issue.executionRunId` and `activeRun.id`, ensure `id !== excludeRunId`.
>    - When `transition.decision` is present, pass `{ excludeRunId: requestingRunId }` into `resolveActiveIssueRun(existing)`.
>    - If there is *another* active run on the issue that does not match `requestingRunId`, that run is still cancelled before reassignment as before.
> 3. **Verify:**
>    - 4 test scenarios in `issue-execution-policy-routes.test.ts`:
>      1) Agent run records approval decision and receives 2xx without being cancelled; wakes next participant.
>      2) Agent run records changes-requested decision and receives 2xx without being cancelled; wakes return assignee.
>      3) Agent run records stage decision and still stops a different active run on the issue.
>      4) Identifies calling run from agent JWT context when `X-Paperclip-Run-Id` header is omitted.

### Issue Summary: PATCH /api/issues/:id recording execution policy stage decision cancels the calling run

**What happened?**
When an agent submits a PATCH to `/api/issues/:id` to record an execution-policy stage decision (e.g., approving an in-review issue or requesting changes), the execution policy handler computes a transition that reassigns the issue to the next participant or returns it to the author.
In `server/src/routes/issues.ts`, the route handler notices that the assignee will change (`assigneeWillChange`) and calls `resolveActiveIssueRun(existing)` to stop the issue's active run via `heartbeat.cancelRun(run.id, "Cancelled before issue reassignment", { errorCode: "issue_reassigned" })`.
Because `resolveActiveIssueRun` does not differentiate between the run sending the request and any other run on the issue, the calling run is cancelled before the database update transaction commits and before the HTTP response is sent.
The cancellation terminates the calling agent's process group (often causing `curl` to exit 137). The run is recorded in Paperclip as `cancelled` with `issue_reassigned` and failed liveness, and subsequent attempts to retry fail with 422 because the decision committed in the background.

**What did you expect to happen?**
1. An agent run that records a stage decision (`transition.decision` truthy) should NOT be cancelled by the reassignment stop logic.
2. The requesting run receives its 2xx HTTP response, is not marked `cancelled` or `issue_reassigned`, and records its own completion disposition.
3. The next participant's wakeup and the stage decision transition commit exactly as before.
4. Any *different* active run on the issue (not matching the requesting run ID) is still stopped before reassignment.

**Steps to reproduce**
1. Configure an issue with an execution policy containing a review stage assigned to Agent A and an approval stage assigned to Agent B.
2. Start an execution run for Agent A on the issue.
3. Agent A calls `PATCH /api/issues/:id` with `status: "done"`, `comment: "Approved"`, and `X-Paperclip-Run-Id: <Agent A Run ID>`.
4. Observe that Agent A's run is cancelled with `issue_reassigned` prior to receiving the HTTP response.

**Paperclip version or commit**
`master` at `efce9356b553a08f77a5877bb0ceac68d2cc4ad8` and release tag `v2026.916.1`.

**Deployment mode**
Self-hosted server and cloud instances.

## What Changed

- `server/src/routes/issues.ts`:
  - Extended `resolveActiveIssueRun(issue, options?: { excludeRunId?: string | null })` to skip interrupting any run whose ID matches `options.excludeRunId`.
  - In `router.patch("/issues/:id", ...)`:
    - Extracted `requestingRunId` from `actor.runId` (JWT claims) or the `X-Paperclip-Run-Id` request header.
    - When `transition.decision` is present, passed `{ excludeRunId: requestingRunId }` to `resolveActiveIssueRun` when stopping runs for reassignment or terminalization.
- `server/src/__tests__/issue-execution-policy-routes.test.ts`:
  - Added regression test: agent run records approval stage decision without cancelling itself and wakes next participant.
  - Added regression test: agent run records changes-requested stage decision without cancelling itself and wakes return assignee.
  - Added regression test: agent run records stage decision and still stops a different active run on the issue.
  - Added regression test: identifies calling run from agent token context when `X-Paperclip-Run-Id` header is omitted.
