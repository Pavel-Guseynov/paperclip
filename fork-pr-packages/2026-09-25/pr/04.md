## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - Agents call tools on remote MCP servers through the Paperclip tool gateway, and the gateway tracks each connection's health
> - When a remote `tools/call` times out, the gateway marks the connection `error`, and the catalog query then hides all of that connection's tools
> - A timeout does not mean the connection is dead. The call may still be running, or it may have finished. So one slow call removes a working integration until a health check runs
> - The replay path can also run the same timed-out write again under its idempotency key, and the result of the first attempt is not known
> - This pull request records an abandoned call as `degraded` and keeps degraded connections in the gateway catalog. It refuses to replay an ambiguous write, keeps conclusive failures fail-closed, and orders health writes so that a stale timeout cannot hide a newer result
> - The benefit is that one slow tool call no longer disables a remote integration, and an ambiguous write is never sent twice

## Linked Issues or Issue Description

No issue exists. This is the bug report, in the shape of `.github/ISSUE_TEMPLATE/bug_report.yml`.

**What happened?**
A remote MCP `tools/call` that exceeded the gateway timeout set the connection's `healthStatus` to `error`. `listToolsForSession` then stopped listing every tool of that connection, and later calls failed with `tool_not_found` while the remote server was healthy.

**What did you expect to happen?**
The abandoned call is reported as a timeout. The connection stays listed, and a later successful exchange restores normal health. A write that timed out is not replayed automatically. A real transport or protocol failure still withdraws the connection.

**Steps to reproduce**
1. Connect a remote MCP server whose `tools/call` answers after the gateway timeout.
2. Call a tool through the gateway, and let the call time out.
3. List tools for a new session. The connection's tools are missing. U writes `markRemoteConnectionHealth(connection, "error", "Remote MCP tool call timed out.")` in `server/src/services/tool-gateway.ts`.

**Paperclip version or commit**
`master` at 7b7c4d4172d6aac14919e2682b702ae87bc17653.

**Deployment mode**
Any deployment that uses remote MCP connections.

Related: #11910 (open) keeps the connection `ok` after one timed-out call. This pull request uses a separate `degraded` state instead, and it adds replay protection, failure classification, and ordered health writes.

## What Changed

- `server/src/services/tool-gateway.ts`:
  - An abandoned call (AbortError) records `degraded` with its dispatch time. The write happens only when no newer observation exists, and it is one conditional `UPDATE`.
  - Conclusive failures record `error` unconditionally, as before:
    - HTTP error
    - JSON-RPC error
    - invalid or oversized response
    - transport failure
  - A recoverable session expiry keeps upstream's behavior and stays unclassified.
  - Every failure carries `failureKind` (`invocation_timeout`, `transport_failure`, `protocol_failure`) in `execution` and in the error details. One reason-code mapping decides the kind.
  - The gateway catalog now includes `degraded` connections. Native-runtime MCP server lists still exclude them, as before.
- `server/src/services/tool-access-policy.ts`: an idempotency-key replay of a timed-out invocation is refused with 409 `ambiguous_invocation_timeout` when the stored invocation was write-capable. A read (`read` or `low`) still replays. A null risk level fails closed. `isWriteCapableRiskLevel()` is now the single definition of write-capable risk levels, also for the existing policy condition.
- `packages/shared/src/constants.ts`: `TOOL_CONNECTION_UNSETTLED_HEALTH_STATUSES` and `TOOL_CONNECTION_SETTLED_HEALTH_STATUSES` (the second is derived from the declared statuses), with a partition test.
- `server/src/__tests__/remote-mcp-timeout-health.test.ts`: a deterministic delayed-server suite on embedded Postgres (17 tests), with no sleeps.

## Risks

- **Behavior change:** `degraded` has other writers, and their connections now also stay in the gateway catalog:
  - a credential that is due for rotation (the 14-day warning, which also covers a credential that already expired)
  - a health probe or catalog refresh whose failure is classified as recoverable (Vercel Connect unavailable, unauthenticated, or not installed)
  - a tool call that cannot resolve its Vercel Connect credential for the same reasons

  Before, their tools were hidden. The warning alone does not show that the connection is unusable. The next call either succeeds, which clears the warning, or the provider rejects it, which marks the connection `error` and withdraws its tools. A connection that is known to be unusable (`error`, `missing_secret`, or switched off through `status`/`enabled`) stays excluded. Personal (per-user) connections already behaved this way.
- A timed-out write can no longer be replayed with the same idempotency key. The caller must use a new key, and the error message says so.
- `mcp_remote_status` maps every non-2xx status to `protocol_failure`. The exact HTTP status stays in `execution.response.httpStatus`.
