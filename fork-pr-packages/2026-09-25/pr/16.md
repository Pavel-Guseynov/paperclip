# fix(tool-access): use catalog tool name as single identity for tool_name profile selectors

## Thinking Path

> - Paperclip provides tool access profiles to govern agent tool permissions using selectors (`all`, `domain`, `tool_name`).
> - Tool profile entries are evaluated across three distinct locations:
>   1. Access decisions: `profileEntryMatches` in `server/src/services/tool-access-policy.ts` (enforced on tool execution and policy checks).
>   2. Effective catalog view / summary: `profileEntryMatchesCatalog` in `server/src/services/tool-access.ts` (used by UI and agent tool summaries).
>   3. Native gateway assembly: `server/src/services/heartbeat.ts` (assembles tool definitions for native adapter runs).
> - In `tool-access.ts` and `heartbeat.ts`, `selectorType === "tool_name"` is matched against the catalog tool name (`candidate.catalogToolName` / `catalogEntry.toolName`, which is the upstream tool name like `searchsql`).
> - However, in `tool-access-policy.ts`, `profileEntryMatches` compared `entry.toolName === ctx.toolName`, where `ctx.toolName` is the runtime gateway tool name (e.g. `openobserve:searchsql` or legacy `mcp.harness-mcp-openobserve:searchsql`), while `ctx.upstreamToolName` carries the catalog tool name `searchsql`.
> - As reported in #11372, an exact `tool_name` rule for `searchsql` appeared allowed in the effective catalog view and heartbeat assembly, but failed at runtime with `denied_by_policy` because `entry.toolName !== ctx.toolName`.
> - If an operator configured `openobserve:searchsql`, runtime matched but the effective summary and heartbeat assembly failed to match.
> - This pull request establishes the catalog tool name (`ctx.upstreamToolName ?? ctx.toolName`) as the single documented identity across all three evaluation points.
> - To migrate existing stored rules without keeping a permanent fallback or dual lookup in the hot access path, a database migration runs on startup (`migrateLegacyProfileToolNameEntries`), rewriting legacy prefixed `tool_name` rules to the catalog tool name while preserving built-in fixtures and plugin tools.
> - With stored entries migrated, `profileEntryMatches` strictly checks `entry.toolName === (ctx.upstreamToolName ?? ctx.toolName)`.

## Linked Issues or Issue Description

Fixes: #11372

### Issue Summary: #11372 Exact tool-name profile entries compare against normalized gateway names and never match

**What happened?**
When configuring an agent tool access profile rule with `selector_type: "tool_name"` and `tool_name: "searchsql"`, the effective tools view and heartbeat assembly recognize the tool as allowed, but invoking the tool or checking runtime policy denies access with `denied_by_policy`.
`profileEntryMatches` in `server/src/services/tool-access-policy.ts` compared `entry.toolName` against `ctx.toolName` (`"openobserve:searchsql"` or `"mcp.openobserve:searchsql"`) instead of the catalog upstream tool name (`"searchsql"`), making exact tool-name rules impossible to reconcile with catalog summaries.

**What did you expect to happen?**
1. An exact `tool_name` profile rule set to the catalog tool name (e.g., `searchsql`) evaluates consistently across all three points: `profileEntryMatches` (access decision), `profileEntryMatchesCatalog` (summary view), and `heartbeat.ts` (native gateway assembly).
2. Existing stored rules containing legacy prefixed names are migrated to the catalog tool name on startup.
3. Built-in fixtures (`mcp-stdio-fixture:*`, `mcp-remote-fixture:*`) and plugin tools (`demo-plugin:*`) remain unchanged.

**Steps to reproduce**
1. Create a tool profile for an agent with rule: `{ selectorType: "tool_name", toolName: "searchsql", effect: "allow" }`.
2. Connect an MCP server exposing `searchsql` (exposed via gateway as `openobserve:searchsql`).
3. Query effective tool access; `searchsql` is listed as allowed.
4. Call `checkToolAccess` or execute the tool through the gateway.
5. The gateway denies execution with `denied_by_policy`.

**Paperclip version or commit**
`master` at `efce9356b553a08f77a5877bb0ceac68d2cc4ad8` and release tag `v2026.916.1`.

**Deployment mode**
Self-hosted server and cloud instances.

## What Changed

- `server/src/services/tool-access-policy.ts`:
  - Updated `profileEntryMatches`:
    `if (entry.selectorType === "tool_name") return Boolean(entry.toolName && entry.toolName === (ctx.upstreamToolName ?? ctx.toolName));`
    This aligns the access decision directly with the catalog tool name identity used by `profileEntryMatchesCatalog` and `heartbeat.ts`.
- `server/src/services/tool-profile-migration.ts`:
  - Added `migrateLegacyProfileToolNameEntries(db)` to scan `agent_tool_profile_rules` where `selector_type = 'tool_name'`.
  - For each rule whose `tool_name` starts with `mcp.` or matches a qualified app-slug format, resolves the catalog tool name from `tool_catalog_entries` for that company and updates the rule.
  - Preserves built-in fixtures (`mcp-stdio-fixture:*`, `mcp-remote-fixture:*`) and plugin tools (`demo-plugin:*`) intact.
- `server/src/services/index.ts`:
  - Exported `migrateLegacyProfileToolNameEntries`.
- `server/src/index.ts`:
  - Added `await migrateLegacyProfileToolNameEntries(db)` to the server startup sequence.
- `server/src/__tests__/tool-gateway.test.ts`:
  - Added regression test `resolves tool_name profile selector against catalog upstream tool name`.
  - Added migration test `migrates legacy mcp-prefixed profile tool_name entries to catalog tool name`.
