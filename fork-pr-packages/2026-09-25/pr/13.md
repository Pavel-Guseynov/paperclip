## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - Contributors and downstream packagers build Paperclip from source with pnpm, and CI installs it with a frozen lockfile
> - The repository pins pnpm 9.15.4 and keeps patches and overrides in two places: `package.json#pnpm` and `pnpm-workspace.yaml`
> - pnpm 10 rejects the frozen lockfile because pnpm 9 generated its patch hashes, and pnpm 11 ignores the configuration in `package.json` (#8827)
> - So a maintained pnpm cannot install the repository with `--frozen-lockfile`
> - This pull request moves the repository to pnpm 11.21.0, makes `pnpm-workspace.yaml` the single pnpm configuration, and adds a policy check that keeps the toolchain consistent
> - The benefit is that current pnpm installs the repository reproducibly, and there is one place to change patches, overrides, and build-script policy

## What Changed

- `package.json`: `packageManager` is `pnpm@11.21.0`. The `pnpm` section is removed, because pnpm 11 reads it no longer. New script `check:pnpm-version`.
- `pnpm-workspace.yaml`: this file is now the single authority. It keeps upstream's current patches and overrides unchanged, including `postgres@3.4.9` and `@lezer/common`. It adds `autoInstallPeers: false`, which pnpm 11 reads only here (it ignores the `.npmrc` key). It also adds an explicit `allowBuilds` policy: every `@embedded-postgres/*` platform package, `esbuild`, and `opencode-ai` are allowed; `cpu-features`, `protobufjs`, and `ssh2` are denied.
- `pnpm-lock.yaml`: regenerated with pnpm 11.21.0 (lockfile version 9.0). See "Risks" for each dependency-version change.
- Every `pnpm/action-setup` step (15 workflows) and `docker/daytona-runner/Dockerfile` use pnpm 11.21.0. This includes `sentry-contract.yml` and the new steps in `runner-protocol-live-evals.yml`.
- Readers of patch declarations now read `pnpm-workspace.yaml` with one shared grammar:
  - `scripts/prepare-bundled-package.mjs` (`readWorkspacePatchedDependencies`)
  - the install fingerprint in `scripts/provision-worktree.sh`
  - the acpx, chat-adapter, CodeMirror, and Lexical manifest contract tests
- The grammar accepts comments and quoted keys or values. An entry that cannot be parsed fails. It is not skipped.
- `packages/paperclip-runner/scripts/check-clean-consumers.mjs` writes the consumer's `pnpm-workspace.yaml` as JSON, which is valid YAML and escapes Windows paths.
- New `scripts/check-pnpm-version-policy.mjs` (`pnpm check:pnpm-version`) with `scripts/check-pnpm-version-policy.test.mjs`. It checks these rules:
  - the package manager, and that `package.json#pnpm` is absent;
  - `autoInstallPeers`, and boolean `allowBuilds` entries;
  - that each declared patch file exists;
  - a pnpm 11.21.0 pin on every setup step (a step without a version fails);
  - the Dockerfile pin and the documented prerequisites;
  - no tracked reference to pnpm 9 outside dated logs and plans.

  The PR policy job runs the check and its test.
- Docs: README, `cli/README.md`, `doc/DEVELOPING.md`, `docs/`, and the runner tutorials give pnpm 11 as the prerequisite. The DEP0169 comments in the provisioning scripts no longer name pnpm 9.

## Risks

- **Lockfile policy (needs maintainer direction).** `.github/scripts/check-pr-lockfile.mjs` and the "Block manual lockfile edits" step in `pr-trusted.yml` reject a `pnpm-lock.yaml` change from any author except the refresh bot on `chore/refresh-lockfile`. This migration needs the regenerated lockfile: pnpm 11 records patch hashes and settings in a new format, and a pnpm 11 frozen install fails against the pnpm 9 lockfile. `doc/DEVELOPING.md` also describes a post-merge refresh. Please say which path you prefer: an exception for this pull request, or this pull request without the lockfile, followed by a bot refresh on pnpm 11.21.0. The branch keeps the lockfile until you decide.
- **CI runs the workflow from `master` (needs maintainer action).** `pr.yml` calls `paperclipai/paperclip/.github/workflows/pr-trusted.yml@master`, so the workflow changes in this pull request do not apply to its own CI run. `master`'s `pr-trusted.yml` sets up pnpm 9.15.4, and this branch declares `packageManager: pnpm@11.21.0`. I did not verify locally how `master`'s `pnpm/action-setup` step reacts to that difference. A maintainer may need to land the workflow pins first, or run this pull request's CI from its own workflow.
- **Dependency versions in the regenerated lockfile.** Four changes come from the `master` lockfile being stale against `master`'s own manifests. `master`'s `pnpm install --frozen-lockfile` fails for the same reason, and CI resolves them inline today:
  - `@openai/codex` 0.153.4 → 0.156.0
  - `@anthropic-ai/claude-agent-sdk` 0.3.263 → 0.3.280
  - `opencode-ai` 1.18.29 → 1.18.32
  - a new `server` devDependency link to `packages/plugins/sdk`

  Two changes are pnpm 11 resolution behavior. pnpm 9's inline resolution keeps the old graph:
  - `jose` 6.2.8 is deduplicated to the existing 6.2.10.
  - The optional peer `debug@4.4.3` now resolves into `follow-redirects@1.16.0`, and so into `axios`, `@slack/*`, `@microsoft/teams.*`, and `@chat-adapter/{slack,teams}`.
- **Build scripts are now deny-by-default.** A new dependency with an install script must be added to `allowBuilds`, or pnpm skips its script.
- `.npmrc` still contains `auto-install-peers=false`. pnpm 11 ignores it (`pnpm config get auto-install-peers` returns `undefined`), and the Dockerfiles copy the file, so this pull request leaves it unchanged.
