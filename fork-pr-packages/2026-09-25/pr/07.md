## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - When an issue enters `in_review`, Paperclip wakes the review participant to start a review run
> - If a blocker exists at that moment, the handoff wake is skipped. Nothing retries it after the blocker clears (#13532)
> - The stranded-issue sweep skips an `in_review` issue that has a pending agent review stage but no participant run, so the issue stays in review with no review run, no retry, and no valid blocker
> - This pull request retries the skipped handoff when the blocker clears and records each attempt durably. After the retry budget is used, it creates one actionable board blocker
> - The benefit is that a review never gets stuck silently, and concurrent or repeated triggers start the handoff exactly once

## What Changed

- `server/src/services/recovery/review-handoff-retry.ts` (new):
  - `reconcileReviewHandoffAfterBlockerClear` decides whether an `in_review` issue with an active agent review stage and no review run needs a handoff. It skips when a valid blocker exists and when the issue is hidden.
  - Each attempt enqueues a wake with the key `review-handoff:<issue>:<stage>:<attempt>`.
  - The decision uses the persisted wake receipt under that key. A refused wake (skipped receipt, or no receipt) consumes an attempt and is reported as skipped. It is never reported as enqueued.
  - When the budget is used, it records one board-owned recovery action through `issueRecoveryActionService.upsertSourceScoped` (`supersedeOnIdentityChange`). `getExecutionBlocker` reports it as the current blocker.
  - The shared `buildExecutionStageWakeContext` moved here from `routes/issues.ts`, which now imports it.
- `packages/db`: a partial unique index `agent_wakeup_requests_review_handoff_retry_idempotency_uq` on `(company_id, idempotency_key)` for `review-handoff:` keys that are not skipped (migration `0284_rapid_prowler`, generated with `pnpm --filter @paperclipai/db generate`). A unique violation is the coalesce signal between processes.
- `server/src/services/recovery/service.ts`:
  - The stranded sweep reconciles the owed handoff instead of skipping the issue.
  - The resolved-dependency backstop reconciles `in_review` dependents of a cleared blocker. It joins on company, applies the visibility condition, and uses the existing candidate limit.
  - Each sweep keeps errors per issue.
- `server/src/routes/issues.ts`: resolving a recovery action awaits the reconciliation after commit. A reconciliation error is logged and does not fail the request.
- Tests (embedded Postgres; only the external adapter boundary is mocked):
  - exactly once under concurrent triggers
  - a durable retry ledger that a fresh service instance continues after restart
  - a refused wake that escalates after the budget, with a bounded number of rows
  - one issue's failure contained within the sweep
  - a hidden issue skipped
  - the route reconciling before it responds
  - the unique index rejecting a second live row for one attempt

## Risks

- Migration `0284_rapid_prowler` adds a partial unique index. No `review-handoff:` keys exist before this change, so the index builds on existing data. `agent_wakeup_requests` is a large table, and Drizzle runs migrations in a transaction, so the index cannot use `CONCURRENTLY`: the build takes a write lock for one table scan. The migration declares this with a `paperclip:migration-safety-ignore large-create-index-not-concurrently` justification, as `0177` and `0193` do. If another pull request takes number 0284 first, the second one to merge regenerates its migration.
- Resolving a recovery action now waits for the reconciliation. That is a small number of queries after commit.
- After the budget is used, the issue stays `in_review` with the board blocker attached. It is not moved to `blocked`.
