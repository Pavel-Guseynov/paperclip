# fix(server): wait for in-flight adapter runs to settle during graceful shutdown

## Thinking Path

> 1. **Understand the Problem and System Context:**
>    - During a graceful server shutdown (`SIGTERM` or `SIGINT`) that does not take the hot-restart skip, the server calls `drainRunExecutionFinalizersForShutdown` to wait for active runs to settle before tearing down the database connection and exiting.
>    - Previously, `drainRunExecutionFinalizersForShutdown` defaulted to a hardcoded 5,000 ms timeout (`timeoutMs ?? 5_000`). If an adapter run required longer to finish stopping (e.g. `antigravity_local`'s graceful stop sequence, which takes ~40 s, or external plugin adapters cleaning up subprocesses), the timeout expired after 5 seconds. The server then closed the database connection underneath the running execution, causing socket errors and dirty process terminations.
>    - Furthermore, when the 5-second timeout expired, the server logged only an `info` message without logging an overrun error failure record naming the pending runs.
>    - Lastly, during the shutdown wait, `drainRunningRunsForShutdown` did not set `shutdownInProgress = true`, allowing queued runs to be dispatched or deferred comment queues to be promoted while the server was actively shutting down.
> 2. **Design the Minimal, Direct Fix:**
>    - Introduce a documented configuration setting for the shutdown drain timeout keeping it comfortably below system supervisors like launchd (`ExitTimeOut` = 120 s):
>      - Setting: `shutdownDrainTimeoutMs` in `config.json` under `server.shutdownDrainTimeoutMs`, env var `PAPERCLIP_SHUTDOWN_DRAIN_TIMEOUT_MS`.
>      - Type: positive integer, default `60000` (60 seconds).
>      - Schema: declared in `packages/shared/src/config-schema.ts` (`serverConfigSchema.shutdownDrainTimeoutMs`) and parsed in `server/src/config.ts`.
>    - In `server/src/shutdown.ts`:
>      - Update the fallback timeout in `drainRunExecutionFinalizersForShutdown` from `5_000` to `60_000`.
>      - Accept optional `getActiveRunIds?: (() => string[]) | null`.
>      - On timeout expiry, emit an error log record naming `pendingRunIds` and `pendingRunCount` before continuing orderly database teardown and shutdown.
>    - In `server/src/index.ts`:
>      - Pass `timeoutMs: config.shutdownDrainTimeoutMs` and `getActiveRunIds: () => heartbeat?.getActiveRunExecutionIds() ?? []` to `drainRunExecutionFinalizersForShutdown`.
>    - In `server/src/services/heartbeat.ts`:
>      - Set `shutdownInProgress = true` in `drainRunningRunsForShutdown` (when draining all runs for shutdown).
>      - Expose `isShutdownInProgress` and `getActiveRunExecutionIds` on `heartbeatService`.
>      - Suppress new run dispatches in `startNextQueuedRunForAgent` and `resumeQueuedRuns` when `shutdownInProgress` is true.
>      - Guard deferred comment promotion in `executeRun` with `!shutdownInProgress`.
>    - Shutdown with no in-flight runs and the hot-restart path behave exactly as before.
> 3. **Verify:**
>    - Regression tests in `server/src/__tests__/shutdown-waits-for-adapter-run-stops.test.ts`:
>      1) An in-flight execution that needs longer than 5 s, but less than the deadline, to finish its stop settles before the database closes and before exit.
>      2) An execution that outlives the deadline produces the overrun failure record, and shutdown still completes.
>      3) No queued or deferred run is dispatched during the wait.

### Issue Summary: Graceful server shutdown cuts off in-flight adapter run stops after 5s and closes database underneath active processes

**What happened?**
During graceful server shutdown (`SIGTERM` or `SIGINT`), Paperclip initiates run execution cleanup. If an adapter or plugin needs longer than 5 seconds to gracefully terminate (for instance, `antigravity_local` requiring up to ~40 seconds for subagents and child processes to finish and save state), the hardcoded 5-second timeout in `drainRunExecutionFinalizersForShutdown` expired. The server immediately proceeded to close the database pool and terminate the server process, leaving adapter child processes orphaned and database queries abruptly severed with socket errors. Furthermore, when the timeout expired, no error was logged reporting the in-flight runs, and new runs could still be scheduled during the drain.

**What did you expect to happen?**
1. Graceful server shutdown waits for in-flight adapter executions to settle stopping up to a configurable deadline (default 60s, keeping it safely below supervisor boundaries such as launchd's 120s `ExitTimeOut`).
2. If the deadline is exceeded, an error failure record is logged explicitly naming the in-flight run IDs (`pendingRunIds`, `pendingRunCount`), and shutdown completes cleanly.
3. No new or queued runs are dispatched while the server is draining for shutdown.
4. Hot-restart skip and zero-run shutdown paths remain unaffected.

**Steps to reproduce**
1. Start an agent run using an adapter that takes >5s to stop (e.g. `antigravity_local`).
2. Send `SIGTERM` to the server process.
3. Observe `bounded heartbeat execution finalizer drain timed out` after only 5 seconds, followed immediately by database pool teardown while the adapter run is still terminating.

## Risks

- **Low:** The drain timeout defaults to 60,000 ms, which is well above typical adapter teardown durations and safely below supervisor termination cutoffs (such as launchd's 120s `ExitTimeOut`). Instances requiring faster teardown can customize `server.shutdownDrainTimeoutMs` or `PAPERCLIP_SHUTDOWN_DRAIN_TIMEOUT_MS`. Shutdown with no active runs exits immediately with no added latency.
