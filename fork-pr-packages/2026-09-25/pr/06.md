## Thinking Path

> - Paperclip is the open source app people use to manage AI agents for work
> - An issue execution policy moves work through review and approval stages, and each stage selects a participant
> - When work comes back from review, the policy excludes the "return assignee" (the author) from the next stage, so the author does not approve their own work
> - An approval stage whose only participant is the return assignee then has no eligible participant. Approval stages are never auto-skipped, so the transition fails with 422 (#4912)
> - This also happens when review approval advances into such an approval stage, and when an intermediate self-review stage should be auto-skipped on the way
> - This pull request keeps the exclusion and falls back to the return assignee only when the exclusion leaves an approval stage empty. It also traverses auto-skippable self-review stages on the approve path, as the entry path already does
> - The benefit is that valid policies with a single approver no longer fail, and stages with other eligible approvers keep independent approval

## Linked Issues or Issue Description

Fixes #4912

Related: #5951 (open) removes the exclusion on the approve path for every stage type. This pull request keeps the exclusion for review stages and for approval stages that name another eligible approver, and adds the fallback and the stage traversal. The two changes touch the same lines, so they conflict.

## What Changed

- `server/src/services/issue-execution-policy.ts`:
  - New `selectEligibleStageParticipant`: it applies the return-assignee exclusion first. If that leaves an approval stage with no participant, it selects the return assignee. Review stages always keep the exclusion, so `canAutoSkipPendingStage` stays the authority for self-review.
  - New `resolveStageAssignment`: one helper for the approve path and the workflow-entry path. It auto-skips consecutive skippable review stages and records the completed state.
  - A genuinely non-skippable stage with no eligible participant still returns a precise 422. The approve-path 422 for a stage with no participants is kept as a defensive guard, because normalization already drops such stages.
- `server/src/__tests__/issue-execution-policy.test.ts`: unit tests cover:
  - review → approval with the return assignee as the only approver
  - approval entry
  - intermediate and consecutive self-review auto-skip
  - a multi-participant approval stage that still selects the other approver
  - the reachable 422
  - unassigned issues
  - identical completed state for approved and skipped completions
- `server/src/__tests__/issue-execution-policy-routes.test.ts`: the #4912 repro and the auto-skip case through `PATCH /api/issues/:id`. Mock implementations are reset per case.

## Risks

- **Behavior change:** with policy `[approval: author]`, an author who moves the issue to `done` is now assigned their own approval stage, instead of a 422. This is the outcome #4912 asks for. When the stage names any other eligible approver, that approver is still selected.
- This pull request does not add concurrency protection for simultaneous approvals. `PATCH /api/issues/:id` computes the transition from an unlocked read, and `issue_execution_decisions` has no unique constraint. This is the same as `master`.
