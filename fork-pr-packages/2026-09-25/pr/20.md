# fix(conversation): support declared adapter conversation continuation

## Thinking Path

> 1. **Understand the Problem and System Context:**
>    - When an agent execution run ends without success (failed, timed out, interrupted by shutdown/SIGTERM, or cancelled with an acknowledged stop), Paperclip evaluates whether the run requires human board intervention via `legacyExecutionNeedsReconciliation`.
>    - For conversational CLI adapters (`claude_local`, `codex_local`, etc.), non-succeeded runs are designed to continue conversation across turns (`CONVERSATION_CONTINUATION_POLICY = "continue_conversation_v1"`), retaining the existing `sessionId` so the next wake resumes the dialogue rather than stranding the issue in a `legacy_execution_requires_reconciliation` board hold.
>    - However, `CONVERSATION_ADAPTER_TYPES` was previously a hardcoded array in `server/src/services/conversation-continuation.ts`. Other adapters, such as `antigravity_local` and custom/plugin adapters, were omitted from this list. As a result, when an `antigravity_local` run was interrupted or stopped, Paperclip treated it as requiring board reconciliation, created an `issueRecoveryActions` hold, and failed to resume the existing session.
> 2. **Design the Minimal, Direct Fix:**
>    - In `@paperclipai/adapter-utils`, introduce the declared capability `supportsConversationContinuation?: boolean` on `ServerAdapterModule` (matching existing pattern `supportsInstructionsBundle`).
>    - In `server/src/services/conversation-continuation.ts`:
>      - Update `isConversationAdapter(adapterType)` to check `findActiveServerAdapter(adapterType)?.supportsConversationContinuation === true` in addition to the built-in `CONVERSATION_ADAPTER_TYPES` list.
>      - Add `getConversationAdapterTypes()` to aggregate built-in and dynamically registered adapters declaring `supportsConversationContinuation: true`.
>      - Update `conversationRunPredicate()` in database queries to use `getConversationAdapterTypes()`.
>    - Preserve backward compatibility: unlisted or undeclared adapters continue to trigger the board reconciliation hold.
> 3. **Verify:**
>    - 6 test scenarios in `server/src/__tests__/antigravity-conversation-continuation.test.ts`:
>      1) An interrupted `antigravity_local` run carries continuation policy and creates no reconciliation hold.
>      2) Acknowledged-cancelled `antigravity_local` run carries continuation policy and creates no reconciliation hold.
>      3) Failed or timed_out `antigravity_local` run is continued, not held.
>      4) Continued wake reuses the stored `sessionId`.
>      5) Run of an unlisted or undeclared adapter is still held for board reconciliation.
>      6) Listed adapter (`claude_local`, `codex_local`) behavior remains unchanged.

### Issue Summary: Interrupted or stopped `antigravity_local` runs create board reconciliation holds instead of continuing conversation

**What happened?**
When an agent using `antigravity_local` (or another modern adapter) runs a task and is interrupted (e.g. by server shutdown/SIGTERM), cancelled with an acknowledged stop, or times out, Paperclip checks `isConversationAdapter`. Because `antigravity_local` was not in the hardcoded `CONVERSATION_ADAPTER_TYPES` array in `server/src/services/conversation-continuation.ts`, the run was not stamped with `conversationContinuation: "continue_conversation_v1"`.
Instead, `legacyExecutionNeedsReconciliation` evaluated to `true`, and `terminalizeLegacyExecution` created an `issueRecoveryActions` row with `cause: "legacy_execution_requires_reconciliation"` assigned to the board, blocking any further automated progress until an operator manually intervened.

**What did you expect to happen?**
1. Adapters declaring conversation continuation support (such as `antigravity_local` via `supportsConversationContinuation: true`) should receive the same conversation-continuation treatment as legacy listed adapters (`claude_local`, `codex_local`).
2. Interrupted, cancelled, failed, or timed out runs carry `conversationContinuation: "continue_conversation_v1"`.
3. No `legacy_execution_requires_reconciliation` board hold is created.
4. The issue's next wake resumes the stored conversation session (`sessionParams.sessionId`) rather than starting a fresh session.
5. Adapters that do not declare conversation continuation remain safely held for operator reconciliation.

**Steps to reproduce**
1. Configure an agent with `adapterType: "antigravity_local"`.
2. Start a run on an issue and trigger graceful shutdown (`SIGTERM`) or an acknowledged stop.
3. Observe that an `issueRecoveryActions` hold is created for the board, and subsequent wakes do not continue the conversation.

## What Changed

- `packages/adapter-utils/src/types.ts`:
  - Added optional `supportsConversationContinuation?: boolean` capability property to `ServerAdapterModule`.
- `server/src/services/conversation-continuation.ts`:
  - Added `getConversationAdapterTypes(): string[]` combining `CONVERSATION_ADAPTER_TYPES` and any active server adapters declaring `supportsConversationContinuation: true`.
  - Updated `isConversationAdapter(adapterType)` to check adapter registry capabilities via `findActiveServerAdapter(adapterType)`.
  - Updated `conversationRunPredicate()` SQL builder to use `getConversationAdapterTypes()`.
- `server/src/__tests__/antigravity-conversation-continuation.test.ts`:
  - Added end-to-end regression tests covering interrupted runs, acknowledged-cancelled runs, failed/timed-out runs, session reuse on subsequent wakes, undeclared adapter hold preservation, and backward compatibility for existing listed adapters.
